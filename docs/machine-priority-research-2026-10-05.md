# Priority machine research — 2026-10-05

Scope set by the owner: all AlgoLaser engravers first, then Ortur, Two Trees, and Creality. xTool is outside the release compatibility target. This is a source inventory and implementation backlog, **not** a compatibility or hardware-validation claim. Product listings change; model/module/firmware identity must be recorded for each tested configuration.

## Current LASERO baseline

`MachineCompatibilityCatalog` currently names only AlgoLaser Alpha MK2, PIXI, DIY KIT MK2, plus two xTool entries. All named targets are refused for direct connection; only manually selected generic GRBL allows it. `KnownMachineProfiles` contains legacy PIXI and Alpha MK2 constants, but `Match` deliberately returns `null`. The existing [compatibility matrix](machine-compatibility-matrix.md) covers those five names and says none is hardware verified. The prioritized manufacturers below therefore require new evidence and implementation; selecting a generic GRBL connection does not establish a model-specific support claim.

## Implementation and evidence order

1. Keep a **discovery-only catalog** for these families, with explicit `unverified` state. Remove xTool from priority UI/help text when product scope is updated, while preserving saved identifiers and avoiding a silent migration. No executable defaults from marketing work areas or advertised speeds.
2. Start direct-control work with one **exact AlgoLaser configuration** and expand to its other modules/firmware only after evidence. For each: model and module markings; firmware/version and `$$`/`$I` transcript; USB VID/PID/driver/baud and handshake; `$30/$32/$130/$131`; homing/origin; coordinate transforms; focus/framing; pause/resume/cancel/disconnect/alarm response; actual interlocks; power ceiling. Obtain the exact manufacturer manual or support confirmation. Repeat for PIXI, Alpha MK2, DIY KIT MK2, MK3, Delta and legacy families independently.
3. Then work through **Ortur**, **Two Trees** and **Creality** by exact model. Group a shared serial adapter only after transcripts and behavior match. Add separate capability handling for conveyor, autofocus/Z, camera, IR/fiber/UV source changes, Wi-Fi/SD, rotary and extensions. Never treat LightBurn/LaserGRBL marketing compatibility as proof that LASERO can safely stream jobs.
4. For each candidate, add offline parser/connection/preflight cases, then supervised tests on real hardware: identity, bounds, beam-off on disconnect/stop/pause, frame with laser off or certified low-power behavior, alarm recovery, and completion. Promote a capability to hardware-verified only for the exact tested model/module/firmware/configuration. Keep every untested route closed.

## Open questions that require hardware or manufacturer evidence

- Exact active model list beyond the dated collections, especially older AlgoLaser and Two Trees units, and whether Aufero is in the Ortur target.
- Firmware/controller variants within each model, including non-GRBL or vendor-mode operation, and whether settings-reporting is complete and trustworthy.
- Electrical/firmware fail-safe behavior of laser output after USB loss, emergency stop, pause and alarm. Documentation and a simulator cannot establish this.
- Distinct work envelopes for add-on rails, rotary, autofocus and module replacement; whether enclosure interlocks are exposed to host software.
